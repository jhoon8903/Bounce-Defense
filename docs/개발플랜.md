## 1. 과제 한줄 요약 + 평가 관점

**한줄 요약:** 세로 화면·탑다운 그리드 아레나에서 하단 발사대(사신)가 위로 볼을 쏴 벽·몬스터에 튕기며(핀볼/Ballz식) 데미지를 주고, 12웨이브를 막으며 웨이브마다 3택 카드로 스킬을 성장시키는 로그라이트 디펜스의 **Stage 1 코어**를 Unity로 재구현.

**리뷰어가 실제로 보는 것 (우선순위 순):**

| 순위 | 평가 축 | 무엇으로 증명하나 |
|---|---|---|
| 1 | **볼 물리 / 게임필** | 등속감·깔끔한 반사·안 끼는 볼·**궤적 미리보기가 실제 볼과 일치**. 게임 정체성이자 영상 첫인상 |
| 2 | **코드 아키텍처 / 확장성** | 3레이어 분리(SO 데이터 / 순수 C# 로직 / 얇은 MonoBehaviour), 순서화된 데미지 파이프라인, 이벤트 훅, 상속 대신 조합 |
| 3 | **스펙 기능 정확성** | 로그라이트 3택 규칙 · 정확한 데미지 계산 · 10개 스킬 동작 |
| 4 | **창의적 가산점** | 코어 재미를 증폭하는 저리스크 추가물 |
| 5 | **표면 폴리시** | 데미지 숫자·화면 흔들림·사운드(영상이 "완성돼 보이게") |

> 핵심 메시지: **코드를 읽는** 클라 프로그래머가 심사한다. "**11번째 스킬 추가 = SO 1개 + 모듈 1개, 코어 루프 무수정**"을 증명하는 것이 최대 차별점.

## 2. 실제 게임 이해 (리서치 + 실플레이 영상 분석)

과제 앱은 실제 서비스 중인 CookApps 게임 **"통통 디펜스 : 핀볼 마스터"(영문 Bounce Defense: Pinball Hero)**. **제출자가 직접 Stage1을 플레이·녹화한 `Stage1.MP4`(211초 풀 플레이)를 프레임 분석**해 아래를 [관찰]로 확정했다.

### ★ 영상으로 확정된 핵심 사실 (Stage1.MP4)

- **스테이지명 "1. Deep Forest"**(어두운 숲). **세로 화면, 탑다운 그리드 아레나 ~7열**. 적은 돌 타일 1칸(멀티셀 블록도 있음)에 개별 HP바.
- **베이스 HP = 300** — 사신(발사대) 바로 아래 초록 바에 숫자 명시. **즉사 아님, HP 감소형**. 적이 하단 방어선 도달 시 감소, 0이면 실패. (내 [추론]이 [관찰]로 확정.)
- **조작**: 튜토리얼 문구 *"Touch the desired location to adjust the firing angle" / "Tap the screen to automatically fire balls"* → **터치로 조준(점선 궤적 미리보기, 벽 반사까지 표시) + 탭하면 연속 자동 발사**. → 실시간 연속, 궤적 미리보기는 코어. (Auto 버튼 있으나 과제 제외.)
- **볼 라이프사이클**: **지속 튕김 + 멀티볼**(여러 볼이 동시에 계속 반사). 턴제 아님 → **실시간 연속 시뮬 확정**.
- **진행 트랙 2개**: (1) 상단 **스테이지 % 바**(0→100%, 100%에 보스) (2) 그 아래 **레벨/XP 바**(킬로 충전 → 레벨업 시 3택 카드). ⚠️ 실게임은 **킬 기반 XP 레벨업**으로 카드가 뜬다(스펙 문구 "웨이브 처치 수 충족 시"와 호환 — §7에서 조율).
- **카드 드래프트 UI**: Active(4)/Passive(2) 슬롯 표시 + **카드 3장**(이름 · ★볼데미지 · 한 줄 설명 · 레벨핍 1/2/3 · 만렙 시 "Max") + **Refresh(리롤) 버튼**(과제 제외).
- **웨이브 12 뒤 BOSS 피날레**(왕관 대형 유닛 + 대형 HP바, 영상 후반 절반). → **과제는 보스 명시 제외** = 우린 **12 노멀 웨이브 + 성공 팝업**까지만.
- **결과(성공) 화면 = "Stage Clear"**: ★3 + "Stage 1 (Normal)" + **Remaining HP %**(별점=잔여 베이스HP로 보임) + 보상 + Back/Claim 버튼. → 우리 성공 팝업의 근거. 별점=잔여HP는 가산점 소재.
- **적 종류(영상+프로젝트 아트 일치)**: 초록 스컬(약), 보라 거미(Spider), ForestDeer, StoneBug, Fluffy. **데미지 숫자**: 흰=노멀, 빨강/주황=크리, 위로 플로팅.

> **남은 [추론]:** '전면/후면'은 이 영상 빌드에 단검 스킬이 없어 직접 관찰 불가 → §2 하단 권장 모델 유지(전면=플레이어 대면/아래, 후면=게이트 대면/위). Day0 스파이크에서 노멀 판정으로 검증.

## 3. 아키텍처 개요

### 씬 구성
- **단일 전투 씬** (단일 스테이지 과제, persistence 불필요). 부트→전투→결과 팝업을 씬 내 상태로 처리.
- 세로 고정. `StageController`가 웨이브/카드/결과 흐름의 진입점.

### 3레이어 분리 (헤드라인 아키텍처)

```
┌─ DATA (ScriptableObject) ─────────────────────────┐
│  SkillDefinition · SkillDatabase · Enemy/Wave/Stage │  런타임 상태 0, 순수 데이터+팩토리
└───────────────────────────────────────────────────┘
        │ 읽음
┌─ LOGIC (순수 C#, UnityEngine 의존 0) ──────────────┐
│  DamageResolver(고정 스테이지) · ModifierRegistry   │  EditMode 단위 테스트 대상
│  CombatEventHub · PlayerLoadout · CardDrawService   │  IRandom(시드) · IClock 주입
│  StatusEffectController · SkillRuntime              │
└───────────────────────────────────────────────────┘
        │ 이벤트 발생 / 호출
┌─ RUNTIME (얇은 MonoBehaviour, 물리 소유) ──────────┐
│  Ball · Enemy · Launcher · WaveController · UI      │  README 핵심 문장:
└───────────────────────────────────────────────────┘   "데미지/스킬/드로우 수학은 Rigidbody를 절대 만지지 않는다"
```

### 핵심 데이터 흐름 (실시간 연속 시뮬레이션)

```
드래그 입력 → AimController → TrajectoryPreview(선택 모터와 동일 수학으로 반사 예측)
   → 놓음 → LaunchController(코루틴, 풀에서 스태거 발사: 노멀 + 보유 액티브당 1개, 최대 5)
   → Ball 이동/튕김 (실시간 연속)
        ├─ 벽 충돌 → CombatEventHub.RaiseWallBounce → MagicMirror 무장(볼별)
        ├─ 적 충돌 → (기본 볼은 튕기며 데미지 / Ghost는 관통) → HitContext 생성
        │     → DamageResolver: Base→Additive%→CritChance(roll)→CritDamage→Round→Apply
        │     → 부가효과 큐(Burn/Freeze/Cluster/Laser) 동일 파이프라인 재귀(chainDepth 가드)
        │     → 적 사망 → RaiseKill → LastMatch 폭발
        └─ 상태이상 틱(Burn DPS, Freeze 타이머)은 IClock 기반으로 항상 진행
   → 킬 카운트 누적 → 웨이브 killsRequired 충족 → (스폰 일시정지) CardDrawService.Draw(3)
        → ChoiceUI → SkillRuntime.Acquire/Upgrade → 재개
   → 웨이브12 클리어 → 성공 팝업 / 베이스HP<=0 → 실패 팝업 (재시작 = 전체 리셋)
```

> **중요(비평 반영):** 스킬이 **초/DPS 단위**(번 4~5초, 냉동 5~7초, 초당 8~12뎀)로 정의됨 → **실시간 연속 시뮬레이션으로 확정**. 웨이브 진행을 "모든 볼 소멸"에 묶지 말고 **킬 수 / 적의 베이스 도달**로 진행(턴제로 세계를 멈추면 초 단위 상태이상이 성립 불가).

## 4. 핵심 설계 결정 (추천 / 반대논리 / README 근거)

### 결정 A — 볼 물리 접근  ★Day0 스파이크로 최종 확정★

두 후보를 `IBallMotor` 인터페이스 뒤에 두고, **Day0 스파이크에서 하나만 선택해 그것만 구현**(둘 다 만들면 물리 작업 2배, 평가 이득 0).

| 후보 | 장점 | 단점 |
|---|---|---|
| **① KinematicRaycast**(권장 우선 검토) — 매 스텝 CircleCast + `Vector2.Reflect`, 잔여거리 소비 루프 | **궤적 미리보기 = 실제 시뮬레이션(완전 일치)**, 등속 정확, 터널링 불가능, Ghost 관통 = 레이어마스크 한 줄 | 코너 이중반사·재히트 오프셋 등 직접 처리 |
| **② Rigidbody2D 하이브리드** — Dynamic·gravity0·Continuous·Interpolate + PhysicsMaterial2D(bounciness=1, friction=0) + FixedUpdate 등속 재정규화 | 코너/다중접촉/충돌이벤트 무료, 코드 적음 | Box2D 에너지 드리프트, bounceThreshold 이하 정지, **미리보기가 1바운스 후 발산** |

**추천: ①을 우선 검토** — 이 장르(Ballz류)는 **미리보기=시뮬레이션**이 핵심이라 거의 다 레이캐스트 기반. 미리보기 정확도가 1순위 평가축(게임필)에 직결. 단, **스파이크가 지터/코너 문제를 못 잡으면 ②로 즉시 전환**(런처·데미지·스킬·UI 무수정).

**반대논리(②가 이기는 경우):** 코너·다중접촉·움직이는 적과의 반사 처리가 직접 캐스트로 복잡해지면, Box2D에 맡기고 등속 재정규화만 얹는 게 코드가 적고 안정적. **다음 중 하나면 ②:** (a) 다중 볼·움직이는 적 충돌에서 레이캐스트 코너 케이스가 감당 안 됨 (b) 남은 시간이 부족.

**README 근거:** 등속·미리보기 일치는 **의도된 게임필 결정**. `IBallMotor` 심으로 물리 백엔드를 가역화. Unity 6 API(`linearVelocity`/`linearDamping`)와 **`Physics2D.bounceThreshold` 필드명은 Day0에 실측 확인**(구버전 `velocityThreshold` 가능성).

### 결정 B — 적 충돌 모델 (비평 P0, 반드시 확정)

- **기본 볼(노멀+액티브)** = 적/블록에 **튕기며 동시에 데미지**(핀볼 정체성). 적은 물리 콜라이더 보유.
- **Ghost 볼** = **관통(트리거, 노바운스)**, 벽은 튕김.
- 근거: 실게임 "볼이 몬스터 타일에 튕기며 데미지"[관찰], 스펙 Ghost "관통, 적에 안 튕김". **모두 트리거로 하면 Ghost가 무의미해지고 핀볼감이 붕괴**(1순위 축).
- 적 물리 셋업 = **Kinematic Rigidbody2D + Collider**. 움직이는 적 + bounciness 1 볼이 에너지 주입할 수 있으니 **스파이크에서 재정규화가 흡수하는지 확인**.

### 결정 C — 스킬 시스템 / 데미지 파이프라인

각 스킬 = **SO 1개(레벨별 값 배열) + `CreateModule(level)` 팩토리** → 런타임 `IBallModule`/`IPassiveModule` 생성. 데미지는 **고정 순서 스테이지 리스트**가 mutable `HitContext`를 처리, 확장은 **`ModifierRegistry`의 self-gating `IDamageModifier`**로. 스킬은 modifier/hook만 등록, **resolver·코어 루프 절대 무수정(개방-폐쇄)**. `CombatEventHub`가 OnLaunch/WallBounce/Hit/Kill 노출. 시드 `IRandom` + `IClock` 주입.

**반대논리(단순 계산기가 이기는 경우):** 고정 10스킬·12웨이브에 레지스트리+이벤트허브는 과할 수 있고, 심(seam)마다 통합 버그가 숨는다. **이기는 조건:** 리뷰어가 격식보다 완성·주시성을 우선하거나 시간이 부족할 때. → **완화:** 추상화를 얇게(좁은 인터페이스, 프레임워크 없음) 유지하고 아낀 시간을 물리에 투입.

### 결정 D — 데미지 계산 순서 (README에 축자 명시)

```
final = round( base × (1 + Σ additive%) × (isCrit ? 1.5 : 1) ),   clamp ≥ 0
스테이지: Base → Additive% → CritChance(roll) → CritDamage(×1.5) → Round(최종만) → Apply
```

- **Additive 버킷(가산 후 1회 곱):** Warm Tin Heart(sourceType==NormalBall 한정) + Magic Mirror(소비형 버퍼) + Ice 상시 추가뎀.
- **Crit:** base 0%에서 시작, Amethyst(전면)/Emerald(후면)만 확률 상승(상호배타, 충돌당 1회 롤). 크리 시 **정확히 ×1.5**(스펙상 크리 데미지를 올리는 스킬 없음 → 공식의 `Σ critDmg%`는 확장용 자리). **직격만 크리**(DoT/AoE/폭발 무크리).
- **반올림:** `round()`, **최종만**(중간 반올림 금지). 예: `8 → Warm Tin L1(+20%) → 9.6 → 10`, 크리 시 `9.6×1.5 = 14.4 → 14`.
- **2차 데미지원(Burn/Laser행/Cluster/폭발):** `canCrit=false` & `canReceiveGlobalModifiers=false`로 자체 flat 주입(더블디핑 방지), 단 **동일 DamageResolver 통과**로 숫자표기·사망이벤트 통일.
- **동시 히트 순서(비평 P1):** Laser 행 다중적·다중접촉·LastMatch 체인은 **결정론적 순서**(예: 적 인덱스 오름차순)로 처리 → 시드 재현성 보장.
- **재귀 가드:** `chainDepth` + sourceType (폭발이 LastMatch 재발동 금지, 특수볼이 Cluster 재발동 금지).
- **Ghost+Magic Mirror:** 관통 시 버퍼는 **첫 적에만 소비**(정의 후 README 명시).
- **가산 채택 이유:** 곱연산은 Warm Tin L3+Ice+Mirror가 비직관적으로 폭발 → 리뷰어 손검산 불가. 가산은 예측·검증 가능.
